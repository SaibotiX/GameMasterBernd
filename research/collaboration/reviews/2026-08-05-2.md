# Collaboration review 2 — 2026-08-05 (the stage-1 design-round session)

Scope: one session — a six-area roadmap revision brief (multi-provider
auth, funded lane, session-data collection, web UI, gap analysis) executed
autonomously into R11–R14 + six commits, then a two-word follow-up and one
question answered. Fairness caveat: nearly all maintainer craft visible
here lives in ONE message (the opening brief); the interactive surface is
thin, so single-session trend claims below are sized accordingly.

## Verdict in one paragraph

The focus was practiced: the first multi-item brief since review 1 arrived
numbered, hierarchically, and the numbering carried the whole round —
completeness was verifiable by id, and the one gap it contains (no point 5)
was *visible* rather than silent, which is exactly the property numbering
buys. The structural strengths did real work again: the brief's own first
clause invoked the guardrail, and that process then caught two conflicts
inside the maintainer's own instructions (subscription-funded play,
subscription OAuth doors) and surfaced them as ⚠ rulings instead of
shipped mistakes. The new residue is architectural anchoring: two
instructions were written against a player's-machine model that strains
against standing R1 (hosted, per-friend containers) without flagging the
tension — the session's one genuine fork, resolved from intent clauses,
but a scope revolution and loose wording should not look identical.
That is the next focus.

### CI-NEW-1 · Instructions floating free of the standing architecture — NEW
- **Definition (one line):** an instruction that touches architecture is
  written against a mental model that strains against a standing registry
  decision, without flagging the tension — loose wording and a deliberate
  scope revolution become indistinguishable.
- **S:** custody (1.1) and session storage (3.2.1). **B:** "stored for
  each user locally, so we don't need to keep it save on a server…
  stored on the Users machine"; "store the game sessions data folders on
  the players machine for as less latency as possible, but how and when
  should we send these Data folders to our server?" — both written as if
  the game runs on the player's machine, while R1 (the roadmap's
  foundation) runs it server-side in per-friend containers. **I:** the
  session faced a real fork — read literally, 3.2.1 overturns R1; read
  loosely, "the player's machine" means their private container/browser.
  The attached intent clauses ("not on a server", "less latency")
  resolved it without a round-trip (auth → browser custody; sessions →
  container-local + shipped), but the resolution was inference where one
  anchor clause — "still hosted per R1; by their machine I mean…" or
  "yes, I mean to revisit R1" — would have made it reading.
