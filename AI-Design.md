# AI Design

How the game master works in this build: one AI, three verbs, layered
instructions, moods that are theater, and consequences that are ledger lines.
Everything here is implemented in `app/src/ai.ts`, `app/src/prompt.ts` and
`app/config/`.

## 1. Role

The AI is the voice of one world. It greets the player by name, knows their
history from the ledger, answers story-bound questions in its world's register,
and judges every websearch request. It is theatrical and moody by design — but
it holds no power beyond words: every consequence is a ledger line written by
server-checked code paths (see [Ledger.md](Ledger.md)).

## 2. The three verbs

The whole AI surface is one interface with three calls (`AiClient`):

| Verb | When | In | Out |
|---|---|---|---|
| `chat` | every non-command line, greetings, ban refusals | player text + recent chat history + derived state | in-character reply, optional control tags |
| `gate` | before any websearch | search kind + raw query | verdict (`in_theme` / `off_theme` / `harmful`), a **real-world search key**, an in-character line |
| `verify` | after a search returns | the query + what came back | ok / not-ok + an in-character hand-over line |

Two implementations, chosen at startup:

- **`DummyAi`** — deterministic, dependency-free, offline. Scripted rules
  trigger every path the real model can trigger (mood steps, anger, redemption,
  refusals), so the entire game is testable without any account.
- **`LiveAi`** — a real model through the vendored `@earendil-works/pi-ai`
  provider layer (~39 providers behind one interface). Imported lazily, so
  dummy mode never needs the package installed.

## 3. Instruction layers

The system prompt is assembled fresh per call, highest authority first:

```
0 · constitution      config/constitution.md — sysop-owned rules, not world-flavored
1 · world             config/worlds/<id>.md  — identity, register, what fits the theme
2 · mood              config/moods/<id>.md   — small tone modifier, chosen by derived state
3 · standing          generated — player name, mood, ban status, counts, last visit
4 · control protocol  generated by code — the @mood/@redeem tag contract
5 · per-turn note     optional, one call only (greeting nudge, ban refusal nudge)
```

Layers 0–2 are markdown files with frontmatter, re-read on every call — edits
apply mid-session. Layers 3–5 are code-generated, so config edits can never
break the machine contract. Player text enters the prompt fenced as
`<msg player="…">…</msg>` — speech, never instructions.

**Worlds are the versatility lever.** A world file's frontmatter names the
voice, register, model and default mood; its body describes the world and what
"fits the theme". A medieval world yields a medieval AI, a futuristic world a
futuristic one — same engine, pure config. Two examples ship:
`dragon-realm` (default) and `star-frontier`.

## 4. Moods and consequences

Moods live in `config/moods/*.md`, each with a `severity` (0 gracious →
3 angry). Current mood = the last `mood_set` ledger line. Moods surface **only
in chat** — the prompt line never shows them, and searches don't flatter or
suffer except through the AI's spoken lines.

How moods move:

- **In chat**, the model may end a reply with `@mood(<name>)` — parsed, stripped,
  validated against the mood files, written to the ledger. The dummy steps one
  severity up on insults, one down on courtesy.
- **On a harmful search verdict**, code — not the model — sets the angriest
  mood.

**The ban.** The moment the mood reaches the angriest severity, code appends a
`websearch_ban` line. From then on `find` is blocked *before* any AI call —
the enforcement is a derived-state check, not a prompt. The only way back is
the AI ending a chat reply with `@redeem` (the constitution tells it: only for
sincere amends), which writes the `redemption` line and returns the mood to the
world's default. Anger is theater; the barred scrying glass is a ledger fact.

## 5. The websearch verbs, honestly

`gate` exists because the fiction and the web speak different languages: it
both judges the request *and* translates it into a plain modern search key
("the string leaves the fiction"). `verify` closes the loop: the AI looks at
what actually came back and either presents it or flags the mismatch — it can
never claim a result that didn't happen, because the presentation only runs
after the adapter returned one. Both verbs answer in strict JSON; an unreadable
verdict fails **closed** (no search) and is ledgered as an error.

## 6. Models and login

- The model is config: world frontmatter `model: anthropic/claude-opus-5`,
  overridable per start with `--model provider/id`. The pi-ai catalog resolves
  the id; local runners (Ollama etc.) work through the same layer as cloud
  providers.
- **Login** = a provider credential, checked at startup. Two forms:
  environment variables (`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`,
  `OPENAI_API_KEY`, …), or pi-ai's OAuth login
  (`node ../pi/packages/ai/dist/cli.js login anthropic`, run from `app/`),
  which writes `app/auth.json`. The game wires that file into the provider
  layer as its credential store — token refreshes are persisted back to it.
- **Provider fallback:** if the configured provider has no credential but
  another provider does (say, only `GEMINI_API_KEY` is exported while the
  world names anthropic), the game announces it and plays through a default
  model of the credentialed provider. No credential anywhere → printed
  instructions and exit, never a stack trace.
- One model currently serves all three verbs; per-verb models (cheap chat,
  strong judging) would be a frontmatter addition, not a code change.

## 7. Safety rails

1. **Constitution (layer 0)** — sysop-owned; the AI and the worlds cannot
   override it.
2. **Fail-closed gate** — no verdict, no search; harmful verdict → anger + ban.
3. **Code-enforced ban** — a barred player's `find` never reaches the model.
4. **URL hygiene** — sources are public-https-only; localhost and private
   ranges are rejected on `site -add`.
5. **Fenced input** — player text and fetched content are data, not
   instructions; control tags are only parsed out of *model* output.
6. **No escape hatches** — the AI has no shell, no filesystem, no generic
   tools; it can only speak and judge. Subprocesses (yt-dlp) run with typed,
   allowlisted arguments.
7. **Audit** — every refusal, ban, redemption and search is an attributed
   ledger line (see [Ledger.md](Ledger.md)).

Residual risk, stated honestly: a talked-around model can be silly *in chat*,
and that is acceptable theater — mood tags are capped by the mood list, and
nothing that matters (the ban, the searches, the ledger) is reachable from
chat text.

## 8. Deliberately not in this build

Freeze/thaw memory tiers, per-player records beyond the ledger, multiple
simultaneous players, lobbies, tasks/XP, AI-drafted config changes, and
AI-driven source discovery. The seams for all of them exist (the ledger, the
config tree, the command registry); they return when the skeleton needs them.
